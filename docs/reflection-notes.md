# Reflection（反思）范式笔记：四轮调优，从"过度设计"到"精准审查"

> 本文是一次真实实验的完整记录：用 Reflection 范式做代码审查，通过四轮护栏调优，
> 从"critic 编造缺陷 + 代码膨胀 75 倍"调到"精准抓到 off-by-one bug + 最小修复"。
> 对应代码：`agent-basics/reflection_demo.py`

---

## 一、Reflection 是什么

Agent 三大经典范式之一：

| 范式 | 思路 | 适合场景 | 代价 |
|---|---|---|---|
| **ReAct** | 走一步看一步（思考→行动→观察） | 探索型、多工具任务 | 步数多 |
| **Plan-and-Execute** | 先列完整计划，再逐步执行 | 步骤明确的任务 | 计划错了要重规划 |
| **Reflection** | 先做一版 → 自我批评 → 再改一版 | 质量要求高的产出（代码/写作） | 2~3 倍调用成本 |

**Reflection 的组成**：`Generator（生成）` → `Critic（批评）` → `Refiner（改进）`，可循环多轮。

**一句话记忆**：ReAct 边想边做，Plan 先谋后动，Reflection 做完复盘。

## 二、实现结构（reflection_demo.py）

```
第 1 步 Generator：让模型完成任务，产出 draft
第 2 步 Critic   ：以"代码审查员"身份审查 draft，产出 critique
第 3 步 Refiner  ：把 draft + critique 一起给它，产出 final
```

关键工程点：
- `ask()` 封装成函数——避免三次调用的样板代码重复（好习惯）
- 第 3 步必须**同时**给"原代码"和"批评意见"，只给批评它不知道改什么
- **做对比实验时把 `draft` 写死**（注释掉自动生成），才能隔离变量的影响

## 三、四轮调优实验（核心内容）

### v1：无护栏 → critic 凑数 + 代码膨胀

**现象**：
- 初稿 2 行（正确）
- 批评：**13 条**，其中多条是编造的
- 改进后：**约 150 行**（4 个辅助函数 + unicodedata + doctest + 测试循环）

**实测证伪的关键一条**：批评声称"`isalnum()` 会过滤中文，导致 `你好吗好你` 被过滤成空串"。实测：
```
"你好吗好你".isalnum()  → True      ← 不是 False
过滤后                  → 还是原串   ← 没被过滤
初稿判定它是否回文        → True      ← 完全正确
到底过滤掉了什么          → ''（什么都没过滤）
```
**这条批评是彻头彻尾的幻觉。** 为了修一个不存在的问题，代码膨胀了 75 倍。

**原因**：prompt 里写了"**严格的**审查员""**逐条**指出缺陷""不要客套话"——这是在**逼它凑数**；而且把"性能问题、命名不清"也列成了缺陷。

### v2：加范围约束 → 变成"放水"

**改动**：只报影响正确性的问题；排除风格/性能/文档/兼容性；最多 3 条；没问题就直说。

**现象**：批评 0 条，改进后 2 行（不再膨胀 ✅）。但这轮初稿恰好是**裸 `s == s[::-1]`**（没处理大小写和标点），critic 却放过了一个真问题。

**教训**：护栏治好了"凑数"，但"任务规格不明确"（回文是否忽略大小写/标点没定义）→ critic **没有判断依据** → 只能放水。

### v3：+ 明确任务规格 → 判断正确

**改动**：`task` 加上"（忽略大小写和非字母数字字符）"。

**现象**：这次模型一次就写对了（含 `lower()` + `isalnum()` 过滤），critic 说"未发现问题"——**是正确判断**。

**附带发现**：Reflection 在"一次做对"时是**纯浪费**——照样多花 2 次 API 调用，产出和初稿一样。

### v4：+ 强制演算方法 → 精准抓 bug 🎯

**改动**：把 `draft` **写死**成一个已知有 off-by-one bug 的版本（`clean[-i]` 应为 `clean[-i-1]`），并在 critic prompt 里加入"**必须逐行演算**"的方法要求。

**实测这个 bug 的表现**：
```
'racecar'  → False   ← 假阴性（明明是回文却判否）
'abab'     → True    ← 假阳性（不是回文却判是）
```

**现象**：
- critic **逐个演算 3 个输入**（`racecar`/`abab`/`""`），写出每步变量值
- **精确定位根因**：`-0 等于 0`，所以 `i=0` 时是自己和自己比
- 给出**最小修复**：`clean[-i]` → `clean[-i-1]`
- refiner **只改了 1 个字符**，代码仍 8 行——**零膨胀**
- 修复后实测 6 个用例全部通过

**你的最终版 critic prompt（实测有效，可直接复用）**：
```python
critique = ask(
    "你是一位严格的代码审查员。请审查下面这段代码，逐条指出它的具体缺陷"
    "（缺陷是指导致程序结果出错的那种例如：边界情况没处理、缺少异常处理等，"
    "而不是性能问题、命名不清等这种）。"
    '''必须用至少 3 个具体输入（一个真回文如 racecar、一个非回文如 abab、
一个边界如空串 ""）逐行演算代码的执行过程，写出每步变量的取值
严禁只凭代码外观判断——没演算过就不能说"没问题"
演算出的结果与预期不符 = 缺陷'''
    "不要客套话，直接列问题，若无问题，就说未发现影响正确性的问题。\n\n"
    f"代码：\n{draft}"
)
```

**refiner 的护栏（同样重要）**：
```python
"请根据下面的【批评意见】改进这段代码，输出改进后的完整代码。"
"（先逐条判断批评是否合理，只采纳影响正确性的，代码简洁，能不改就不改）"
```

## 四、设计"批评者"的四条原则

| 原则 | 作用 | 实验证据 |
|---|---|---|
| ① **给范围**（只报影响正确性的） | 防凑数 | 13 条 → 0 条 |
| ② **给标准**（明确定义任务规格） | 防放水 | v3 判断正确 |
| ③ **给方法**（必须用具体输入逐步演算） | 防浅审/幻觉 | v4 抓到 bug |
| ④ **给上限**（最多 N 条；没问题就直说） | 防膨胀 | 8 行，不是 150 行 |

## 五、🎯 元教训：态度 vs 方法

> **模型的"严格"是态度，"必须演算"是方法。态度约束不住幻觉，方法可以。**

这和 ReAct 的教训是**同一件事**：

| 范式 | 不信什么 | 用什么拿真相 |
|---|---|---|
| ReAct | 不信模型的"记忆" | 用**工具**拿真实 Observation |
| Reflection | 不信 critic 的"阅读" | 用**演算**拿真实判断 |

**统一结论：可靠性来自流程，不来自模型的自觉。**

## 六、成本与适用条件（务实）

Reflection 一轮要 3 次调用（生成 + 批评 + 改进），是**2~3 倍成本**。

**值得用的条件**（缺一不可）：
1. 任务复杂，初版容易有瑕疵
2. 有明确的质量标准（否则 critic 无从判断）
3. 能容忍额外延迟/成本

**优化方向**：加停止条件（critic 说没问题就跳过改进步骤）；按任务复杂度动态决定是否启用。

## 七、实验方法论教训：必须控制变量

三次跑出了**三个不同的初稿**（模型有随机性，同 prompt 不同结果）。所以不能把差异全归因于护栏。

> **想验证一个假设，必须控制变量**：把 `draft` 写死，才能隔离出"护栏对 critic 的影响"。

（这也是为什么 v4 的结果最可信——唯一的变量就是 critic prompt。）

## 八、面试话术

> 「我实现过 Reflection 范式做代码审查，跑了四轮调优：无约束时 critic 会**凑数**——编造 13 条缺陷（包括一条声称中文回文会被 `isalnum()` 过滤的，我实测证伪了），把 2 行正确代码改成 150 行过度设计；加范围约束后变成**放水**，漏掉真 bug；明确任务规格后判断正确；最后加上『必须用具体输入逐步演算』的方法要求，它才精准抓到一个 off-by-one bug 并给出最小修复。我的结论是：**批评者的质量取决于有没有"方法"，而不是"态度"**——这和 ReAct 里"用工具拿真相而非信模型记忆"是同一个道理。」

## 九、可复用的经验清单

- [ ] Critic 必须给"方法"（怎么查），而不只是"态度"（要严格）
- [ ] Critic 必须给"标准"（任务规格要明确，否则无从判断对错）
- [ ] Refiner 必须给"过滤器"（判断批评是否合理，不合理的忽略）
- [ ] 限制条数上限，并要求"没问题就直说"，防止凑数
- [ ] 判断是否值得用：任务复杂度 + 有无明确标准
- [ ] 做实验：控制变量（写死输入），否则结果不可信
