# RAG 学习与调优笔记（含"清洗误删知识"教训）

> 从零搭起一个 RAG 学习笔记问答机，并针对"三步法答不好"做了一次完整调优。
> 对应代码：`rag-demo/`（build_index.py / ask.py / inspect_chunks.py）。

---

## 一、RAG 是什么（一句话）

**RAG = 先"检索你的资料库"，再"基于检索到的内容回答"。**

```
普通模型： 问题 → 靠训练时学过的知识硬答（没学过就编）
RAG 模型： 问题 → 先从向量库检索相关内容 → 模型只能基于资料答（查不到就说不知道）
```

**最大的价值：防乱编 + 能用私有知识。** 你笔记里没有"量子引力"，它回答"笔记里没有相关内容"——不是因为它傻，而是因为没有依据、诚实拒绝。

## 二、两个阶段 & 六个步骤（最小心智模型）

**切分 → 向量 → 入库 → 检索 → 生成**（5 个词记住整条链）

### 阶段一：建索引（一次性）—— build_index.py
```
你的笔记(docs/*.md)
  → ① 清洗(clean)  去掉Markdown噪音符号
  → ② 切分(chunk)  按标题切独立小节
  → ③ 向量化(embedding)  每段文字→一串数字
  → ④ 存入向量库(chromadb)
```

### 阶段二：查询（每次）—— ask.py
```
用户提问
  → ⑤ 提问也变向量
  → ⑥ 相似度检索：找最相关的 TOP_K 段
  → ⑦ 把"检索到的笔记 + 问题"拼进 prompt，让模型作答
（模型【只】基于检索结果回答，查不到就直说）
```

## 三、关键概念（用大白话）

| 概念 | 白话 | 类比图书馆 |
|---|---|---|
| embedding 向量 | 把文字变成一串数字，意思相近的数字也接近 | 给每段内容贴索引标签 |
| 切分 chunking | 把长文档切成独立小节 | 把书按章节拆散上架 |
| 向量数据库 | 存向量 + 快速找相似 | 图书数据库 |
| 检索 | 找和提问最接近的几段 | 管理员取几本书 |
| TOP_K | 每次最多取几段资料 | 最多递给你几本书 |

## 四、你在实战中验证过的三个点

1. **提问和文档必须用【同一个】embedding 模型**——不同模型产生的向量在"不同坐标系"，无法比较相似度（像米尺vs英尺）。
2. **向量化噪声**：Markdown 的 ```、反引号、|、--- 会稀释语义关键词，需要清洗。
3. **错误信息也是设计**：检索不到时，模型的兜底（"笔记里没有相关内容"）让它保持诚实。

## 五、⚠️ 最重要的教训：清洗过度会"误删知识"（务必记住）

**现象**：加了清洗后，"三步法是什么"反而答不出，而检索明明命中了正确段落。

**根因**：`clean_markdown` 把所有 **```代码块内容**全删了。但你的笔记里，**大量真正的知识就写在代码块里**（例如 day6-challenge 的"三步法"，正文就在 ``` 代码块内）：

```markdown
## 三步法
```
第 1 步：写函数 → ...
第 2 步：加 JSON Schema → ...
第 3 步：注册 → ...
```
```

清洗把 ``` 里面内容全删 → 该小节只剩标题"三步法"，**没有"三步法具体内容"** → 模型合理地说"没有相关内容"。

**教训（RAG 调优的铁律）**：
> **清洗去噪时，先保内容、后去噪。** 别为了去掉 ``` 符号，把藏在代码块/表格里的知识也一并删了。宁可保留一点噪声，也要保住知识本身。

**修复**：清洗时只去掉 ``` 围栏行，**保留代码块内的文字行**。改完重新建索引，问题解决。

## 六、完整调优过程（面试能讲的真实案例）

| 迭代 | 改动 | 结果 |
|---|---|---|
| ① 初始版 | 固定字数切分 + 不清洗 | "三步法"检索错 + 答不出 |
| ② 诊断 | 写 inspect_chunks.py 看全部 chunk + 检索排序 | 发现"检索排序差 + 代码噪音 + 切分散" |
| ③ 调优1 | 清洗 + 按标题切分 | chunk 完整、检索第1名正确，**仍答不出** |
| ④ 深挖 | 查看命中的 chunk 原文 | **定位到"清洗误删了代码块内容"** |
| ⑤ 调优2 | 清洗改为"保代码块内容" | **成功答出** ✅ |

## 七、可调参数 & 各自影响

| 参数(config.py) | 作用 | 调大 | 调小 |
|---|---|---|---|
| `CHUNK_SIZE` | 切分大小 | 块更大、更"完整"但答案颗粒度粗 | 更细但可能拆散完整知识点 |
| `CHUNK_OVERLAP` | 相邻块重叠 | 防切断句子 | 更省空间 |
| `TOP_K` | 检索返回段数 | 上下文更全但噪音多 | 更聚焦但可能漏知识 |
| `EMBEDDING_MODEL` | 向量模型 | 更大更准(如 bge-base-zh)但慢 | 更轻更快 |

**残留的权衡**：你现在清洗时删掉了"表格行"。表格里其实有值钱知识（如类型对照表），这是牺牲了这部分知识换取正文更干净。实际项目常用"重排序(rerank)"或"分块解析表格"来兼顾，是进阶方向。

## 八、把 RAG 做成 Agent 工具（进阶，你会了这个用法）

把 rag-demo 的检索封装成 `rag_query` 函数，注册进 `tools.py` 的 TOOLS/TOOL_FUNCTIONS，就实现了"Agent 也能查私有知识库"。

**关键工程点**：
- embedding 模型 + 向量库是**重量级对象** → 用"懒加载 + 全局缓存"，避免每次调用都重新加载（否则很慢）。
- 工具函数内部可以"再调一次大模型"（`rag_client.rag_query` 里就调了基元律动去"基于检索结果生成"）。**一个工具可以是一个 mini-Agent**——这是高阶用法。

```
你："我的笔记里三步法是什么"
  → main.py 模型看到 rag_query 工具
  → 调用 rag_client.rag_query("三步法是什么")
  → 内部：检索笔记 + 让模型基于笔记回答
  → 结果回传 → main.py 模型组织最终回答
```
